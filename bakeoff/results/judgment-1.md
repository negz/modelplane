# E2E bake-off: judgment 1

Tags: **[option]** is a weakness that would persist however well the option was built. **[prototype]** is one a better implementation would fix. Line numbers are per file, in each option's worktree. Log lines are in `/tmp/bakeoff/runs/`.

## Scores

| Option | Legibility | Failure output | Cost of next test | Code we'd own | Toolchain | Coverage | Robustness |
|---|---|---|---|---|---|---|---|
| shell | 3 | 4 | 3 | 4 | 5 | 4 | 3 |
| unittest | 5 | 5 | 4 | 4 | 5 | 4 | 3 |
| pytest | 4 | 4 | 5 | 3 | 4 | 4 | 4 |
| chainsaw | 3 | 3 | 2 | 5 | 2 | 3 | 4 |

Totals: unittest 30, pytest 28, shell 26, chainsaw 22.

## Evidence

### shell

- **Legibility 3.** Each check opens with a readable contract, such as `check A1 "An OpenAI chat completion naming ... returns 200"` (`e2e/tests/serving.sh:38`), and failures say why: `--- FAIL A1: ... got HTTP 401: Client authentication failed.` (`shell-faulted.log:18`). But check bodies are bash parsing. C2 is a nested JSONPath range string split with IFS and matched against `;Exists=;` (`tests/placement.sh:48-52`), and response bodies are read with sed (`lib.sh:125-128`). **[option]**: bash has no JSON without adding jq.
- **Failure output 4.** Every expected result landed. A1, A4 and B1 failed. A2 and C1 passed. A3, A5 and B2 skipped as consequences. C2 failed naming `cert-manager/bakeoff-rogue`, and a per-check summary closes the run (`shell-faulted.log:18-138`). Docked because the extra A6 passes vacuously on `HTTP 401` (`serving.sh:131`, log:61), A9 fails rather than skipping as a consequence, and the run took 461 s. **[prototype]**
- **Cost of next test 3.** The harness is small (`check`, `pass`, `fail`, `skip`, `eventually` and `request`, `lib.sh:34-117`), so a status-code check is about 10 lines. Anything asserting response shape, which is where #368 points, means textual JSON matching. The notes concede that "A reformatted log would break A5" (`BAKEOFF.md:56-57`). **[option]**, softened if jq were added.
- **Code we'd own 4.** 159 lines sit beyond the tests (`lib.sh` 128, `test.sh` 31), all simple functions. Bring-up stays in `run.sh`, now 234 lines. It's simple, but untyped and has no tests of its own.
- **Toolchain 5.** Adds nothing: bash, kubectl, the crossplane CLI and the pinned curl image (`BAKEOFF.md:44`). `shellcheck -x` passes (I ran it). Needs bash 4 or later, which nix provides.
- **Coverage 4.** A1 to A5, B1 to B3, C1, C2 and D1 are all present. It's the only prototype that kept `run.sh`'s other verify checks (A6 to A9) and wired the suite into `run.sh --verify` (last line of `e2e/run.sh`). D1 runs only when named, and refuses to start without `E2E_CP_CONTEXT` (`tests/clouds.sh:17-20`). Placement is expressed awkwardly (see Legibility).
- **Robustness 3.** The waits and traps are good: retries of 120 s on A1, 60 s on A4, and 360 s then 120 s on B1 (`serving.sh:44,82`, `lifecycle.sh:69,76`), and EXIT, INT and TERM traps that tear down (`lifecycle.sh:26-27`). But B's teardown only deletes the namespace (`lifecycle.sh:18`). The orchestrator verified that this wedges when a ModelDeployment is still in the namespace (`findings.md:21-44`), and B3 skips in exactly that case, when there are no replicas (`lifecycle.sh:118-119`). A2 and A6 to A9 each send a single request. **[prototype]**

### unittest

- **Legibility 5.** Tests are 2 to 5 lines, each with a docstring carrying its ID (`e2e/tests/test_serving.py:81-107`), which `-v` prints beside the result (`unittest-faulted.log:10-29`). Failures carry the HTTP body and the conditions of what should have served it (`explain`, `test_serving.py:73-79`; log:66-68). B1 to B3 depend on running in order, which is documented (`test_lifecycle.py:64-69`) and real: unittest sorts methods by name (CPython 3.12 `unittest/loader.py:69,226`).
- **Failure output 5.** This is exactly the expected pattern. A1, A3, A4, A5 and B1 failed. A2, C1 and B3 passed. B2 skipped with the reason "isn't serving (HTTP 401)". C2 failed naming `cert-manager/bakeoff-rogue tolerates [{'operator': 'Exists'}]` (`unittest-faulted.log:11-29,49-53`). A5 lists the records it saw, all `status: 401`, which points at the fault on its own (log:102-110). The run took 244 s.
- **Cost of next test 4.** The helpers are plain functions (`kube.poll`, `kube.items` and `gateway.Client.post`), so a new check is one method. There are no fixtures or markers, and no parametrising beyond `subTest`, so each class writes its own setUpClass, cleanup and failure-message helpers (`explain`, `state`). **[option]**
- **Code we'd own 4.** 205 lines of helpers (`kube.py` 105, `gateway.py` 100), with no framework hooks, plus a `ty-e2e` check and wider lint scope in `nix/checks.nix`. Being stdlib-only forces workarounds, such as parsing YAML with `kubectl create --dry-run` (`test_lifecycle.py:35-43`).
- **Toolchain 5.** It imports only the stdlib, and runs on the dev shell's python3 and kubectl (`BAKEOFF.md:30-34`). ruff check and format pass (I ran them). CI would need python3 in the e2e app's runtimeInputs, which isn't done.
- **Coverage 4.** A to D are all present. D1 is gated by `skipUnless(MODELPLANE_E2E_EKS_CONTEXT)`, and every run prints the reason (`test_clouds.py:46`; log:9). The suite isn't wired into `run.sh`, so `--verify` still runs its own copy of A1 to A5. D1 applies and deletes the getting-started platform under its real names (`test_clouds.py:55-56`), so it could delete a maintainer's own. **[prototype]**
- **Robustness 3.** A has no retries at all (`BAKEOFF.md:63-64`, `test_serving.py:81-107`), and it runs straight after B has changed the gateway's routes, because modules run in alphabetical order. Subprocess calls have no timeout (`kube.py:35-37`, `gateway.py:71-76`), so a hung kubectl hangs the run. Teardown only deletes the namespace (`test_lifecycle.py:61`), which is the wedge case in `findings.md`. In its favour, class cleanups run even when setUpClass fails (CPython `suite.py` `_handleClassSetUp`). Both healthy runs passed, with no flakes.

### pytest

- **Legibility 4.** Test names state the check (`test_a2_request_without_valid_key_returns_401[no key]`). A failure shows the response, a note that it was "Still failing after waiting 120s for ..." (`e2e/wait.py:37`), and a section listing the conditions of the Modelplane resources (`pytest-faulted.log:116-135`). It loses a point to fixture indirection. `model` is a string fixture in `test_serving.py:44-64` but a setup and teardown fixture in `test_lifecycle.py:49-63`, and fixtures bring the clusters up (`conftest.py:88-103`).
- **Failure output 4.** A1, A3, A4, A5 and B1 failed, A2 passed both cases, C2 failed naming the pod, and the short summary lists every failure (log:163, 368-375). But B2 passed on `401: Client authentication failed.` (log:29-32), a false pass: its skip guard checks RoutingReady, not whether B1 ever got a 200 (`test_lifecycle.py:94-96`). **[prototype]** The run took 715 s, because every failing request check waits 120 s (`test_serving.py:39`).
- **Cost of next test 5.** Tests reuse session fixtures by name (`client`, `endpoints`, `control_plane` and `workload`), parametrising and markers are built in, and the `diagnose` marker gives any failing test its diagnostics for free (`conftest.py:56-75`). One dent: the lifecycle fixture is a 125-line copy of the platform ModelDeployment (`manifests/lifecycle/10-model-deployment.yaml`, `BAKEOFF.md:61`). **[prototype]**
- **Code we'd own 3.** Helpers and conftest come to 446 lines (conftest 170, kube 123, gateway 111, wait 42), including pytest hook wrappers and collection hooks. On top of that are a 300-line Python bring-up that replaces `run.sh` and a uv2nix venv (`nix/python.nix`). The brief required the bring-up, but the project would still own it.
- **Toolchain 4.** It adds pytest and four transitive dependencies to `uv.lock` as an `e2e` group, a uv2nix venv for the app, and a workflow change that drops `-- --verify`. That fits the repo's Python, uv and Nix stack, and it reuses the `schemas/python` models. The "uv.lock rebuilds every function image" cost isn't specific to pytest (see the fairness section). ruff passes.
- **Coverage 4.** A to D are all present, and D1's gating is the most natural of the four: `@pytest.mark.cloud("eks")`, skipped unless `--cloud=eks`, with the reason in every summary (`conftest.py:78-85`; log:368). The Python bring-up passed on a fresh environment (`pytest-bringup.log`: 11 passed in 928 s), though with the nix app bypassed and nodeCount patched (`findings.md:80-89`). Deleting `run.sh` drops its unknown-model, mTLS, port 80 and `/v1/models` checks (`BAKEOFF.md:39-41`). D1's teardown deletes ClusterProviderConfig `default` and Secret `aws-creds` (`test_clouds.py:57-58`), the names the getting-started guide uses. **[prototype]**
- **Robustness 4.** Every kubectl call has a timeout (`kube.py:32`), waits re-raise the last assertion, and teardown deletes in order: ModelService, then the ModelDeployment in the foreground and waited on, then the namespace (`test_lifecycle.py:58-63`). The faulted run shows that teardown working (log:38-42). Against it: retrying every check for 2 minutes makes failures slow, and even the negative check A2 is retried until it sees a 401 (`test_serving.py:91-95`).

### chainsaw

- **Legibility 3.** Step names and descriptions map to the IDs (`a1-openai-chat-completion`), and resource asserts read well (`local/lifecycle/chainsaw-test.yaml:64-75`). But the HTTP checks are shell folded into YAML (`local/serving/chainsaw-test.yaml:109-118`), and the cross-namespace checks are JMESPath like `local/placement/chainsaw-test.yaml:89`. Some failures hide the cause. A3 reports `invalid character 'C' looking for beginning of value` rather than the 401 (`chainsaw-faulted.log:178-180`).
- **Failure output 3.** A1, A3, A4 and A5 failed independently, A2 and C1 passed, C2 named the pod (`["cert-manager/bakeoff-rogue"]: lengths of slices don't match`, log:124-126), and cleanup ran (log:330-337). But once B1 failed, B2 and B3 never ran and weren't reported as skipped: at v0.2.15, `pkg/runner/runner.go:352-358` stops the test at the first failed operation that lacks `continueOnError`. The summary is per test ("Failed tests 3", log:338-347), so finding which check failed means reading 348 interleaved lines. **[option]**, partly: the stop can be avoided, but nothing reports steps that didn't run.
- **Cost of next test 2.** Bindings don't cross steps. `runner.go:191` hands each step the test's context, not the previous step's (I verified this). So the serving test repeats the model and endpoint bindings five times (`serving/chainsaw-test.yaml:94-98, 122-126, 164-168, 192-196, 220-224`), and runs to 280 lines for five checks, against 137 to 168 for the other options. Scripts can't wait for something to become true, so those waits are hand-written shell loops (`BAKEOFF.md:47-49`). A plain resource assert is cheap, but the behavioural HTTP tests planned in #368 are not. **[option]**
- **Code we'd own 5.** Only 60 lines sit outside the tests (`test.sh` 24, `.chainsaw.yaml` 20, `curl.yaml` 16). The complexity moves into the tests and into the tool.
- **Toolchain 2.** It adds a Go binary (kyverno-chainsaw v0.2.15 from nixpkgs, one line in the flake), and with it a new language for contributors: Chainsaw's YAML, JMESPath with Chainsaw's extensions, and embedded shell. The tool is pre-1.0 and its APIs are alpha (v1alpha1 and v1alpha2). The builder needed six citations of Chainsaw's source to document its limitations (`BAKEOFF.md:43-59`). `chainsaw lint test` passes on all four test files (I ran it).
- **Coverage 3.** A to D are all present. Lifecycle fits it most naturally (apply, assert, delete and error). Serving is shell in YAML, and placement needs `x_k8s_list` JMESPath. D1 is gated only by living outside `local/` (`test.sh:24`), because `skip: true` has no CLI override (`BAKEOFF.md:58-59`). B2 and B3 stop when B1 fails, and the suite isn't wired into `run.sh`.
- **Robustness 4.** Its cleanup is the strongest of the four. Even on failure, it deleted the ModelService, then the ModelDeployment, then the namespace (log:330-337), which avoids the namespace wedge. Every operation has a timeout (`.chainsaw.yaml`). Against it: tests run in parallel by default against a shared gateway, A2 to A4 send a single request each, and bindings are a snapshot taken once (`placement/chainsaw-test.yaml:5-7`).

## Ranking

1. unittest (30)
2. pytest (28)
3. shell (26)
4. chainsaw (22)

unittest and pytest both parse JSON properly, and both give readable assertions and structured failures. unittest does it with no new dependencies, and produced the cleanest faulted run. Its weak spots (single requests with no retry, namespace-only teardown, no call timeouts) are all prototype fixes. pytest scales better per test and has the best diagnostics and gating. But it owns about twice the helper code plus a Python bring-up, and its prototype showed a false pass and took 12 minutes to report failures. The gap is small: if the suite will grow a lot, pytest's lower cost per test could outweigh its up-front cost. Shell adds nothing and reported failures well, but bash with JSON matched as text makes #368's behavioural tests expensive. Chainsaw owns the least code, but it adds a pre-1.0 DSL, repeats itself because bindings don't cross steps, and silently stops lifecycle at the first failure.

## Biggest risk if adopted

- **shell:** Test logic lives in bash with no JSON parser. The prototype already matches JSON as text (`lib.sh:125-128`, `serving.sh:110`), and #368's response-shape and streaming tests would make that the norm.
- **unittest:** A home-grown framework creeps in. With no fixtures, markers or diagnostic hooks, each new scenario adds its own setup, cleanup, message helpers and reliance on method-name order, until `kube.py` and `gateway.py` become a private pytest.
- **pytest:** Retries everywhere hide intermittent failures. Wrapping every check in a 2-minute wait makes failures slow, and lets vacuous passes like B2 slip through. The new CI path, from the nix app through the uv2nix venv to `pytest --bring-up`, has never run.
- **chainsaw:** To write HTTP-heavy tests as shell inside YAML, maintainers have to learn a pre-1.0 tool's semantics: per-step bindings, stopping at the first failure, snapshot bindings and namespace injection. Its builder had to read Chainsaw's source to find them.

## Where the experiment is unfair or misleading

1. **The faults are loud and uniform.** F1 fails every authenticated request, so it tests how a suite handles consequences, not how it diagnoses, and no fault targets B3 or causes intermittent failures. That favours chainsaw, which went unpunished for stopping at B1 because B3 would have passed. It also favours unittest and chainsaw, whose single requests can't show a flake.
2. **Two serial healthy runs on a settled environment can't measure flakiness.** That favours designs without retries (unittest's A, and chainsaw's A2 to A4), and it hides chainsaw's parallel tests racing each other on a shared gateway.
3. **The wall times aren't like for like.** Chainsaw runs its three tests in parallel (`findings.md:18-19`), and the others run serially. The summary table favours chainsaw, though pytest-xdist or backgrounded scripts would narrow the gap.
4. **The briefs differ in scope.** Only pytest had to port bring-up (300 lines, plus the nix app and the workflow), which counts against it under "code we'd own" and "toolchain". Conversely, only pytest's integration was verified end to end on a fresh environment. Shell's wiring of `run.sh --verify` into `test.sh` never ran, and unittest and chainsaw didn't wire up CI at all. On that point the evidence favours pytest.
5. **The uv.lock rebuild isn't pytest's cost.** `findings.md:55-59` blames pytest's `uv.lock` change for a rebuild of every function image. I evaluated `packages.x86_64-linux.compose-usages-amd64.drvPath` in upstream main and in all four worktrees, and got five different paths. That includes shell, whose diff touches only `e2e/`. `clean.log`, whose output is `run.sh`'s, also built 258 derivations. The images rebuild on any change to the source, so every option pays this cost, and presenting it as pytest's disfavours pytest.
6. **"Code we'd own" beyond the tests favours chainsaw.** Its complexity lives in the tests and in an external pre-1.0 tool, and this criterion counts neither.
7. **The capacity was raised in the environment, not in the code.** nodeCount 5 was set on the running environment, but every option's committed manifests still say 1. So in a real CI run, B's second model has no declared capacity in all four. That's neutral between the options, but it makes B look closer to ready for CI than it is.
8. **The first faulted unittest run was lost.** Only the rerun's log was kept, so there's no telling whether the killed run's B1 was slow, stuck or fine.
